# Правила разработки проекта KoW Tracker (Kingdom of Winners)

## 1. Методология GitFlow

Все изменения в кодовой базе проекта ведутся строго по методологии **GitFlow**:

1. **Ветка `master`**:
   - Является производственной (production-ready) веткой.
   - Прямые коммиты в ветку `master` **категорически запрещены**.
   - Код попадает в `master` только через слияние релизных веток (`release/vX.Y.Z`) или хотфиксов (`hotfix/vX.Y.Z`).

2. **Ветки разработки (`feature/*` и `bugfix/*`)**:
   - Любая новая функциональность разрабатывается в отдельной ветке `feature/<краткое-название>`.
   - Исправления ошибок ведутся в ветках `bugfix/<краткое-название>` или `fix/<краткое-название>`.
   - Ответвление происходит от актуального состояния `master`.

3. **Релизный процесс (Release Workflow)**:
   - При завершении разработки фичи или набора задач создается релизная ветка: `release/vX.Y.Z`.
   - В релизной ветке производятся финальные операции подготовки:
     - Повышение номера версии в `package.json` по SemVer (`MAJOR.MINOR.PATCH`).
     - Внесение описания изменений в `CHANGELOG.md` по стандарту Keep a Changelog.
     - Запуск и проверка полного набора тестов (`npm test`).
   - Слияние в `master` производится исключительно с флагом `--no-ff` (no fast-forward) с сохранением истории:
     ```bash
     git checkout master
     git merge --no-ff release/vX.Y.Z -m "Merge branch 'release/vX.Y.Z' into master"
     ```
   - На мерж-коммит релиза на `master` обязательно ставится аннотированный тег:
     ```bash
     git tag -a vX.Y.Z -m "Release vX.Y.Z: <Краткое описание релиза>"
     ```
   - После успешного слияния и тегирования временные ветки (`feature/*`, `release/*`) удаляются:
     ```bash
     git branch -d feature/<name> release/vX.Y.Z
     ```

4. **Формат сообщений коммитов (Conventional Commits)**:
   - Сообщения должны начинаться с понятного префикса:
     - `feat:` — новая функциональность
     - `fix:` — исправление ошибки
     - `docs:` — документация, спеки, планы
     - `test:` — добавление или правка тестов
     - `refactor:` — переработка кода без изменения логики
     - `chore:` — технические задачи, обновление версий, релизы

## 2. Стандарты качества и тестирование (TDD)

1. **TDD подход**:
   - При реализации нового функционала или исправлении багов сначала пишется падающий тест (фаза RED), затем код (фаза GREEN).
2. **Комплексная верификация перед релизом**:
   - Модульные тесты логики: `node logic.test.js`
   - Тесты базы данных SQLite: `node db.test.js`
   - Интеграционные тесты API: `node api.test.js`
   - Проверка синтаксиса: `node -c app.js && node -c server.js`
   - Все тесты должны быть зелеными без единого сбоя (0 failures).

## 3. Архитектура и безопасность

1. **База данных SQLite и Docker**:
   - База данных SQLite хранится в файле `data/kow.db` (монтируется в Docker volume `./data:/app/data`).
   - Файлы `*.db` добавлены в `.gitignore` и никогда не должны попадать в репозиторий git.
   - Любые изменения схемы БД должны сохранять обратную совместимость с экспортом/импортом `kow_v2`.
2. **Ролевая модель RBAC (Р5, Р4, Р3)**:
   - Права доступа проверяются на бэкенде: Р3 изолирован в личном кабинете; Р4 и Р5 имеют доступ к гильдейским операциям; только Р5 может управлять ролями пользователей и импортировать данные.
   - Любые эндпоинты обновления профиля игрока должны санитизировать чувствительные поля (`rank`, `id`).
3. **Нулевые внешние зависимости сервера**:
   - Бэкенд (`server.js`, `db.js`) использует нативные возможности Node.js (`node:http`, `node:sqlite`, `node:crypto`). Не добавлять лишних npm-зависимостей без явного согласования.
