## 1. Введение и анализ проблем

### 1.1. Проблема 1: Отсутствие инструментов блокировки и удаления пользователей
1. **Текущее состояние:**
   - В разделе **«🔐 Пользователи»** (`#page-users`) доступны только:
     - Изменение ранга (`Р3`, `Р4`, `Р5`);
     - Настройка делегированных прав (`🛡️ Права`);
     - Принудительная смена пароля (`🔑 Пароль`).
   - Кнопки **«Заблокировать»** и **«Удалить пользователя»** отсутствуют.
2. **Риски и последствия:**
   - Если боец покинул альянс или нарушил правила, администратор (Р5) вынужден придумывать обходные пути (менять пароль на случайный текст).
   - При смене пароля **уже открытые активные сессии (`sessions`) не сбрасываются**, и пользователь продолжает иметь доступ к данным гильдии, пока не истечет срок жизни сессии или cookie.
   - В базе данных накапливаются неактуальные аккаунты без возможности очистки.

---

### 1.2. Проблема 2: Несоответствие сектора при регистрации пользователя
1. **Текущее состояние:**
   - В форме регистрации (`#auth-form-register`) есть поле **«Название сектора (базы в игре)»** (`auth-reg-player-name`).
   - Пользователь вводит название (например, `[A433]Commander`).
   - В таблице пользователей («Пользователи») в столбце «Персонаж» отображается введенное имя.
   - **Но по факту персонажа (сектора) нет:**
     - Сектор либо создается пустым без базового каталога офицеров (`officers: []`), из-за чего при входе в Личный кабинет и в таблице секторов нет офицеров;
     - Если сектор с таким именем уже был предварительно занесен в гильдию (например, импортирован из таблицы без привязки к аккаунту `user_id IS NULL`), система не связывает пользователя с существующей базой, а создает дубликат или теряет привязку;
     - Если заявку пользователя отклоняют («Отклонить»), пользователь удаляется из `users`, а созданный под него сектор остается «висеть» в `players` как сирота с `user_id = NULL`, засоряя список секторов альянса;
     - При одобрении заявки связка `users.player_id` ⇄ `players.user_id` не валидируется и не гарантирует доступность сектора в Личном кабинете новичка.

## 2. Архитектура и требования к реализации

### 2.1. Модуль управления доступом пользователей (Блокировка и Удаление)

#### А. Блокировка / Разблокировка пользователя
1. **База данных (`db.js`):**
   - В таблицу `users` добавляется колонка `is_blocked INTEGER NOT NULL DEFAULT 0`.
   - Добавляется автоматическая мягкая миграция в `initDb()`:
     ```sql
     ALTER TABLE users ADD COLUMN is_blocked INTEGER NOT NULL DEFAULT 0;
     ```
   - Метод `blockUser(userId, isBlocked)`:
     - Устанавливает `is_blocked = 1` или `0`.
     - При `is_blocked = 1` немедленно удаляет все активные сессии пользователя из таблицы `sessions`:
       ```sql
       DELETE FROM sessions WHERE user_id = ?;
       ```
2. **Безопасность и RBAC (`server.js`):**
   - Эндпоинт `POST /api/users/:id/block` (только для роли `r5`):
     - Принимает `{ blocked: true / false }`.
     - Защита от самоблокировки: запрещено блокировать самого себя (текущего администратора Р5).
     - Возвращает обновленного пользователя.
   - В `verifySession(token)`:
     - Если пользователь заблокирован (`is_blocked === 1`), немедленно возвращает `null` (401 Unauthorized), даже если токен сессии передан.
   - В `POST /api/auth/login`:
     - Если `user.is_blocked === 1`, возвращается ошибка `403 Forbidden`: `ACCOUNT_BLOCKED` (*«Доступ к аккаунту заблокирован руководством гильдии»*).
3. **Интерфейс (`app.js`, `index.html`, `style.css`):**
   - В таблице раздела «🔐 Пользователи»:
     - В колонке «Статус»: если `is_blocked === 1` — отображается яркий бейдж `⛔ Заблокирован`, иначе `✓ Активен` / `⏳ Ожидает`.
     - В колонке «Действия» добавляется кнопка:
       - Если активен: `⛔ Заблокировать` (с подтверждением `confirm`).
       - Если заблокирован: `✅ Разблокировать`.

---

#### Б. Удаление пользователя
1. **База данных (`db.js`):**
   - Метод `deleteUser(userId, { deleteSectors = false } = {})`:
     - Удаляет все сессии пользователя: `DELETE FROM sessions WHERE user_id = ?`.
     - Удаляет токены привязки Telegram и отвязывает Telegram-чат.
     - Обработка секторов пользователя:
       - Если `deleteSectors === false` (по умолчанию): секторы сохраняются для гильдии, но отвязываются от удаляемого аккаунта (`UPDATE players SET user_id = NULL WHERE user_id = ?`).
       - Если `deleteSectors === true`: секторы пользователя удаляются (вместе с их офицерами и привязками к ивентам).
     - Удаляет запись из `users`: `DELETE FROM users WHERE id = ?`.
2. **Безопасность (`server.js`):**
   - Эндпоинт `DELETE /api/users/:id` (только для роли `r5`).
   - Защита: запрещено удалять аккаунт `admin` и текущего залогиненного пользователя Р5.
   - Опциональный query-параметр или body: `deleteSectors: boolean`.
3. **Интерфейс (`app.js`):**
   - В столбце «Действия» таблицы пользователей добавляется кнопка `🗑️ Удалить` (красная кнопка).
   - По нажатию открывается модальное окно подтверждения с информацией:
     - Имя пользователя и его персонаж;
     - Чекбокс: *«Также удалить сектор игрока из гильдии»* (по умолчанию выключен, чтобы база сектора осталась в гильдии).
     - Кнопка *«Подтвердить удаление»*.

### 2.2. Модуль гарантированного создания и привязки сектора при регистрации

1. **Регистрация с указанием названия базы (`registerUser` в `db.js`):**
   - Если указано `playerName`:
     - **Шаг 1 (Поиск существующего сектора):**
       Проверяем, существует ли уже в таблице `players` свободный сектор с таким именем:
       ```sql
       SELECT id FROM players WHERE LOWER(name) = LOWER(?) AND (user_id IS NULL OR user_id = '');
       ```
       - Если найден свободный сектор:
         - Привязываем его к новому пользователю: `UPDATE players SET user_id = ? WHERE id = ?`.
         - Устанавливаем `users.player_id = player.id`.
       - Если свободный сектор не найден:
         - Создаем **новый сектор** через `createPlayer({ name: playerName, rank: 'r3', userId })`.
         - **Гарантированная инициализация офицеров:** для нового сектора автоматически создаются записи в `player_officers` для всех офицеров из `officer_catalog` с начальными параметрами (`level: 0`, `coupons: 0`, `stars: 0`, базовые навыки), чтобы сектор сразу был полностью функционален в интерфейсе, калькуляторе и личном кабинете.
         - Записываем полученный `playerId` в `users.player_id`.

2. **Одобрение заявки (`approveUser` в `db.js` и `server.js`):**
   - При одобрении пользователя (через Web-интерфейс «Одобрить (Р3/Р4)» или через Telegram кнопку `approve_user:<id>`):
     - Обновляется `is_approved = 1`, выставляется одобренный ранг (`r3` или `r4`).
     - Если у пользователя есть `player_id`:
       - Синхронизируется `players.rank = rank` и `players.user_id = user.id`.
       - Гарантируется, что сектор появляется во всех выборках `getPlayers()` и доступен новичку при первом входе в Личный кабинет.

3. **Отклонение заявки (`rejectUser` в `db.js` и `server.js`):**
   - При отклонении заявки новичка:
     - Если пользователь регистрировался с новым сектором (который был создан автоматически при регистрации и не имеет прокачки/склада/истории):
       - Автоматически удалять этот временный сектор, исключая появление пустых «призрачных» секторов в гильдии.
     - Если пользователь был привязан к ранее существовавшему сектору гильдии:
       - Сектор гильдии сохраняется и освобождается (`players.user_id = NULL`).

## 4. Критерии приемки

1. Администратор (Р5) в таблице пользователей видит кнопки блокировки и удаления.
2. При блокировке пользователь мгновенно вылетает из системы (сессии аннулируются) и не может войти под своим паролем.
3. При удалении аккаунт удаляется, а сектор отвязывается либо удаляется по выбору администратора.
4. При регистрации новичка с указанием сектора создается полноценный рабочий сектор с офицерами каталога, сразу видимый после одобрения.
5. Все тесты (`npm test`) зеленые с 0 ошибок.
6. Разработка ведется строго по GitFlow в ветке `feature/user-management-and-registration-sector`.
