## 1. Цели, Контекст и Ценность (Intent & Why)

### 1.1. Контекст
Текущее приложение KoW Tracker является автономным клиентом в браузере (`localStorage`). Вся статистика, список офицеров и расчеты происходят локально. Для гильдии требуется единое централизованное решение в Docker-контейнере, куда каждый участник может зайти со своего смартфона или компьютера, вести данные своих офицеров и заявляться на места в ивентах, а руководство гильдии (Р4/Р5) подтверждает регистрации и распределяет награды.

### 1.2. Цели (Goals)
1. **Бэкенд и База Данных в Docker:**
   - Полноценный бэкенд на Node.js (Express) с встроенной СУБД SQLite (файл `data/kow.db`).
   - Готовые `Dockerfile` и `docker-compose.yml` для развертывания одной командой `docker compose up -d`.
   - Сохранение возможности локального запуска без Docker (`npm start`).
2. **Ролевая модель доступа (Р5, Р4, Р3):**
   - **Р5 (Глава гильдии):** Полный доступ ко всем разделам (игроки, матрица, каталог офицеров, ивенты, подтверждение регистраций, управление пользователями и назначение ролей).
   - **Р4 (Чиновник):** Доступ к управлению гильдией (просмотр всех игроков и их запасов, матрица прокачки, создание и проведение ивентов, подтверждение регистраций новичков, запуск автоподбора).
   - **Р3 (Рядовой):** Изолированный личный кабинет. Доступ только к своим данным (свои офицеры, свои запасы, сектор, персональный симулятор прокачки) и к просмотру предстоящих ивентов. Доступ к чужим профилям, общей матрице гильдии и редактированию ивентов закрыт.
3. **Личный кабинет игрока (Р3):**
   - Ввод и обновление уровней, купонов и звёзд своих офицеров.
   - Добавление новых офицеров из каталога в свой список.
   - Управление текущими запасами (купоны, пазлы, сундуки) и параметрами сектора (VIP, уровень секретности).
4. **Онбординг игроков (Саморегистрация + Одобрение Р4/Р5):**
   - Игрок самостоятельно регистрируется через форму (логин, пароль, выбор своего игрока из списка гильдии или ввод нового имени).
   - Аккаунт переходит в статус ожидания (`is_approved = 0`).
   - Р4 или Р5 видят список заявок на регистрацию в панели управления и нажимают «Одобрить» / «Отклонить».
   - После одобрения игрок входит в личный кабинет.
5. **Система регистрации на ивенты (Заявки):**
   - В карточке предстоящего ивента игрок (Р3, Р4, Р5) может подать заявку: выбрать офицера для прокачки и **желаемое место** (1-е место, 2-е место, 3-е место, 4–10 место или «Любое подходящее»).
   - Игрок видит статус своей заявки («Вы записаны на 2 место»).
   - Р4/Р5 видят список всех поданных заявок при редактировании ивента.
   - Алгоритм автоподбора (`smartAutoPick`) учитывает эти заявки: приоритет отдаётся игрокам, подавшим заявку на конкретное место, при строгом соблюдении защиты от перерасхода купонов (`deficitCoupons >= placeCoupons`) и правила «один игрок — одно место».

### 1.3. Не-цели (Non-Goals)
- Создание внешней OAuth2 / SSO авторизации (Google, Discord, Telegram) на первом этапе. Используется простая и надежная авторизация по логину/нику и паролю/пин-коду, с возможностью смены пароля в кабинете.
- Создание системы чата внутри приложения (координация гильдии по-прежнему идет в мессенджерах игры/Telegram).

### 1.4. Анти-цели (Anti-Goals)
- Нельзя допустить утери ранее введенных данных: бэкенд поддерживает импорт существующего JSON-файла `kow_v2` при первой инициализации базы данных.
- Нельзя переписывать или дублировать математическое ядро (`logic.js`): модуль подключается на бэкенде напрямую через `require('./logic.js')`.

## 2. Варианты реализации (Approaches)

### Рассмотренные варианты:
1. **Вариант 1 (Выбран): Node.js + Express + SQLite + Docker.**
   - *Плюсы:* 100% переиспользование протестированного ядра `logic.js` на бэкенде. Минимальное потребление памяти (образ Node.js Alpine), надёжные транзакции SQLite в отдельном томе (`./data`), отсутствие внешних зависимостей. Запуск в Docker и локально.
   - *Минусы:* SQLite файл рассчитан на один сервер/инстанс (что идеально для нужд гильдии из 50-150 человек).
2. **Вариант 2: Python (FastAPI) + PostgreSQL + Docker.**
   - *Плюсы:* Автодокументация Swagger.
   - *Минусы:* Необходимость полного переписывания `logic.js` (симуляция, автоподбор, расчет дней) на Python, риск расхождения алгоритмов, усложнение стека отдельным контейнером PostgreSQL.
3. **Вариант 3: Облачный BaaS (Supabase/Firebase).**
   - *Плюсы:* Отсутствие своего бэкенд-кода.
   - *Минусы:* Зависимость от зарубежных облачных провайдеров, невозможность автономного запуска в закрытом контуре/Docker.

**Решение:** Реализуем Вариант 1 по выбору пользователя.

### 3.1. Схема базы данных SQLite
В файле `data/kow.db` создаются следующие таблицы:

1. **`users`**:
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `username` TEXT UNIQUE NOT NULL (логин/ник)
   - `password_hash` TEXT NOT NULL
   - `rank` TEXT NOT NULL DEFAULT 'r3' ('r3' | 'r4' | 'r5')
   - `is_approved` INTEGER NOT NULL DEFAULT 0 (1 — одобрен, 0 — ожидает подтверждения Р4/Р5)
   - `player_id` INTEGER NULL REFERENCES players(id)
   - `created_at` TEXT NOT NULL

2. **`players`**:
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `name` TEXT NOT NULL
   - `real_name` TEXT DEFAULT ''
   - `rank` TEXT NOT NULL DEFAULT 'r3'
   - `vip_level` INTEGER DEFAULT 0
   - `confidentiality_level` INTEGER DEFAULT 0
   - `power` REAL DEFAULT 0
   - `kills` REAL DEFAULT 0
   - `stock_coupons` INTEGER DEFAULT 0
   - `stock_puzzles` INTEGER DEFAULT 0
   - `stock_chests` INTEGER DEFAULT 0
   - `updated_at` TEXT NOT NULL

3. **`player_officers`**:
   - `id` TEXT PRIMARY KEY (e.g. `po-123456`)
   - `player_id` INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE
   - `catalog_id` TEXT NOT NULL
   - `name` TEXT NOT NULL
   - `level` INTEGER NOT NULL DEFAULT 0
   - `coupons` INTEGER NOT NULL DEFAULT 0
   - `stars` INTEGER NOT NULL DEFAULT 0

4. **`officer_catalog`**:
   - `id` TEXT PRIMARY KEY
   - `name` TEXT NOT NULL
   - `type` TEXT NOT NULL ('Танк' | 'ПТ' | 'Пехота' | 'Гарнизон' | 'Осада')
   - `generation` INTEGER NOT NULL DEFAULT 7
   - `coupon_per_puzzle` INTEGER NOT NULL DEFAULT 500
   - `medals_before_training` INTEGER DEFAULT 690
   - `medals_training` INTEGER DEFAULT 900
   - `medals_total` INTEGER DEFAULT 1590

5. **`event_types`**:
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `name` TEXT NOT NULL
   - `color` TEXT NOT NULL DEFAULT '#8b5cf6'
   - `places_json` TEXT NOT NULL -- JSON массив мест и купонов

6. **`events`**:
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `type_id` INTEGER NOT NULL REFERENCES event_types(id)
   - `date_from` TEXT NOT NULL
   - `date_to` TEXT NOT NULL
   - `note` TEXT DEFAULT ''
   - `assignments_json` TEXT NOT NULL DEFAULT '[]' -- JSON массив утвержденных назначений

7. **`event_registrations`** (Заявки игроков на ивенты):
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `event_id` INTEGER NOT NULL REFERENCES events(id) ON DELETE CASCADE
   - `player_id` INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE
   - `officer_id` TEXT NOT NULL
   - `desired_place` INTEGER NOT NULL -- 1, 2, 3, 4 (где 4 означает 4–10) или 0 (любое)
   - `created_at` TEXT NOT NULL
   - UNIQUE(event_id, player_id) -- один игрок может подать одну заявку на конкретный ивент

8. **`stock_history`**:
   - `id` INTEGER PRIMARY KEY AUTOINCREMENT
   - `player_id` INTEGER NOT NULL
   - `date` TEXT NOT NULL
   - `coupons` INTEGER NOT NULL
   - `puzzles` INTEGER NOT NULL
   - `chests` INTEGER NOT NULL

## 4. Спецификация REST API

### 4.1. Авторизация и Саморегистрация (`/api/auth`)
- `POST /api/auth/register`: `{ username, password, playerId?, playerName? }`
  - Создает пользователя с `is_approved = 0`.
  - Если это самый первый пользователь в системе, он автоматически становится `rank = 'r5'`, `is_approved = 1` (главный администратор).
  - Возвращает `{ success: true, pendingApproval: true }`.
- `POST /api/auth/login`: `{ username, password }`
  - Проверяет пароль и `is_approved === 1`. Если `is_approved === 0`, возвращает `403` с сообщением: «Аккаунт ожидает подтверждения Главой (Р5) или Чиновником (Р4)».
  - Возвращает `{ token, user: { id, username, rank, playerId } }`.
- `POST /api/auth/logout`: инвалидация сессии.
- `GET /api/auth/me`: данные текущего пользователя и связанного игрока.
- `POST /api/auth/change-password`: смена своего пароля.

### 4.2. Управление заявками на регистрацию и пользователями (Р4 и Р5)
- `GET /api/users/pending` (Р4, Р5): список пользователей, ожидающих одобрения (`is_approved = 0`).
- `POST /api/users/:id/approve` (Р4, Р5): утверждение аккаунта (`is_approved = 1`, назначение роли `r3` или `r4`).
- `POST /api/users/:id/reject` (Р4, Р5): отклонение заявки и удаление аккаунта.
- `GET /api/users` (только Р5): полный список пользователей.
- `PATCH /api/users/:id` (только Р5): смена роли пользователя или сброс пароля.

### 4.3. Личный кабинет игрока (`/api/my-profile`)
- `GET /api/my-profile`: возвращает профиль текущего игрока, список его офицеров, запасы и параметры сектора.
- `PUT /api/my-profile`: обновление сектора (VIP, секретность, мощь, киллы) и запасов (купоны, пазлы, сундуки).
- `POST /api/my-profile/officers`: добавление офицера из каталога.
- `PUT /api/my-profile/officers/:id`: обновление уровня, купонов, звёзд офицера.
- `DELETE /api/my-profile/officers/:id`: удаление офицера из своего профиля.

### 4.4. Ивенты и Заявки
- `GET /api/events`: список ивентов.
  - Для Р3: скрываются приватные запасы других игроков в назначенных слотах, отдается флаг `myRegistration` для текущего игрока.
  - Для Р4/Р5: полная детализация, включая список поданных заявок (`registrations`).
- `POST /api/events/:id/register` (Заявка на ивент):
  - Тело: `{ officerId, desiredPlace }`.
  - Записывает или обновляет заявку в `event_registrations`.
- `DELETE /api/events/:id/register`: отмена своей заявки.
- `POST /api/events/:id/autopick` (только Р4/Р5):
  - Запускает серверный `smartAutoPick` с учетом заявок.
  - **Правила разрешения конфликтов (Tie-breaking):**
    1. Игроки, заявившиеся на конкретное место (`desiredPlace === place.place`), имеют приоритет над незаявившимися.
    2. При конкуренции нескольких заявок на одно место побеждает кандидат с наибольшим оставшимся дефицитом купонов (`deficitCoupons` DESC). При равном дефиците — по боевым очкам/уровню.
    3. Если кандидат уступил в конкуренции за желаемое место, алгоритм пробует назначить его на последующие места (2, 3, 4...), если его дефицит удовлетворяет условию отсутствия перерасхода.
    4. Заявка с `desiredPlace = 0` («Любое подходящее») распределяется на лучший свободный слот с достаточным дефицитом раньше кандидатов без заявок.

### 4.5. Импорт и Экспорт данных
- `POST /api/admin/import` (только Р5): загрузка JSON-файла бэкапа `kow_v2` с перезаписью или слиянием.
- `GET /api/admin/export` (Р4, Р5): выгрузка полного состояния базы в JSON.
- **Авто-бутстрап:** При первом старте, если база `kow.db` пуста, сервер автоматически импортирует демо-состав игроков и офицеров и создает начального администратора Р5 (`admin` / `admin123`).

## 5. Пользовательский интерфейс (Frontend)

### 5.1. Экран авторизации и регистрации
- Вкладка **«Вход»**: логин и пароль.
- Вкладка **«Регистрация»**: логин, пароль, выпадающий список существующих свободных персонажей гильдии либо поле «Создать нового персонажа».
- Сообщение после регистрации: «Заявка отправлена руководству гильдии (Р4/Р5). После одобрения вы сможете войти.»

### 5.2. Адаптивное меню по ролям
- **Верхняя панель (Topbar):**
  - Справа вместо ручного селектора роли отображается бейдж авторизованного пользователя:
    `[Р5 Глава] Командор` или `[Р3] Шторм` + кнопка «Выйти» 🚪.
  - Для Р4/Р5 отображается бейдж новых заявок на регистрацию (например: `🔔 2 заявки`).
- **Боковое меню (Sidebar):**
  - **Для Р3 (Рядовой):**
    - 👤 **Мой кабинет** (Профиль, Мои офицеры, Мои запасы, Персональный симулятор).
    - 📅 **Календарь ивентов** (Предстоящие события, подача заявок).
  - **Для Р4 и Р5 (Чиновники и Глава):**
    - 📅 **Календарь ивентов** (Создание, планирование, автоподбор).
    - 👥 **Игроки гильдии** (Полный список, статистика, карточки).
    - 🎖️ **Офицеры** (Каталог офицеров игры).
    - ⚙️ **Типы ивентов** (Настройка наград и купонов).
    - 📊 **Калькулятор и Аналитика** (Сводная матрица гильдии и симулятор).
    - 👥 **Заявки на регистрацию** (Одобрение новичков Р4/Р5).
    - 🔐 **Пользователи** *(только Р5)* (Управление ролями и аккаунтами).

### 5.3. Личный кабинет игрока (Р3)
- Блок параметров: VIP-уровень, Секретность, Мощь, Убийства.
- Блок запасов: Универсальные купоны, Золотые пазлы, Сундуки выбора.
- Карточки офицеров игрока:
  - Интерактивные звёзды (с подсказкой до следующей звезды).
  - Уровень (слайдер или числовой ввод до 180).
  - Текущие купоны на уровне.
  - Расчёт оставшегося дефицита купонов до 180 уровня.
  - Кнопка «Добавить офицера» (выбор из официального каталога).
- Персональный симулятор прокачки: прогноз достижения 180 уровня с учетом ежедневного притока от VIP и секретности.

### 5.4. Интерфейс регистрации на ивенты
- В календаре у карточки предстоящего ивента кнопка: **«Зарегистрироваться на ивент»** (или «Изменить заявку», если уже подана).
- При клике открывается модальное окно:
  - Выбор своего офицера, которого игрок качает.
  - Выбор желаемого места: `🥇 1 место (12 500)`, `🥈 2 место (6 500)`, `🥉 3 место (3 500)`, `🎖️ 4–10 место (2 750)` или `Любое подходящее`.
  - Предупреждение/подсказка: если текущий дефицит офицера меньше награды за 1 место, система предупреждает («У офицера остался дефицит всего 4 000 купонов — награда за 1 место приведет к перерасходу, рекомендуется занять 2 или 3 место»).
- В модальном окне редактирования ивента у Р4/Р5:
  - Вкладка/блок «Заявки игроков (X подан(о))».
  - Кнопка «Автоподбор с учетом заявок»: автоматически расставляет игроков по их заявкам, заполняя оставшиеся места кандидатами с наибольшим дефицитом.

## 7. План тестирования и верификации
1. **Unit-тесты logic.js:** сохранение и расширение существующих 18 тестов новыми сценариями автоподбора с учетом заявок (`smartAutoPickWithRegistrations`).
2. **API Integration-тесты:**
   - Саморегистрация: создание пользователя со статусом `pending`, проверка блокировки входа до подтверждения.
   - Одобрение: Р4 одобряет заявку, пользователь успешно логинится как Р3.
   - Защита эндпоинтов: Р3 получает 403 Forbidden при попытке запросить чужие данные игроков или изменить ивент.
   - Заявки на ивенты: Р3 успешно подает заявку, Р4 видит её в списке заявок.
   - Запуск `smartAutoPick`: распределение мест с учетом приоритета поданных заявок.
3. **Docker проверка:**
   - Сборка образа `docker build -t kow-tracker .`.
   - Запуск контейнера, проверка доступности UI и API, сохранение данных в файл на хосте при перезапуске контейнера.
