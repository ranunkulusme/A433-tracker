# Спецификация дизайна: Секторы (1:N к Пользователям) и декомпозиция управления офицерами

**Дата:** 2026-10-26  
**Ветка:** `feature/sectors-and-officer-management`  
**Статус:** Draft (на согласовании)

---

## 1. Назначение и контекст (Intent & Why)

### Проблема
1. **Разрыв между Пользователями и Игровыми базами:** В текущей системе сущность пользователя (`users`) и сущность игрока (`players`) слабо связаны: в таблице и карточке игрока не отображается, какому пользователю сайта принадлежит персонаж. Кроме того, один пользователь мог быть привязан только к одному игроку (`users.player_id`), тогда как в стратегиях вроде *Kiss of War* у одного игрока почти всегда есть несколько игровых баз (основной аккаунт/мейн и 1–2 фермы/твина).
2. **Перегруженность модального окна редактирования:** Чтобы изменить параметры даже одного офицера (уровень, купоны или навыки), требуется нажать «Редактировать» в шапке карточки игрока, что открывает гигантское модальное окно (`#modal-player`), где объединены статистика, склад и длинный список всех офицеров. При этом сама страница игрока содержит статичную таблицу без возможности точечного редактирования или добавления офицера прямо на месте.
3. **Терминологическое несоответствие:** Термин «Игрок» вносит путаницу с «Пользователем». Реальный человек — это Пользователь сайта, а его игровые базы в альянсе — это **Секторы**.

### Цели
1. Ввести сущность **«Сектор»** (вместо «Игрок») и модель связи **1 Пользователь ➔ $N$ Секторов**.
2. В карточке и списке секторов отображать владельца (`👤 @username` либо бейдж `Без владельца`).
3. Предоставить соклановцу (Р3) в «Моем кабинете» переключатель между всеми своими секторами и возможность добавить новую базу (`+ Добавить сектор`).
4. Декомпозировать карточку сектора:
   - В модалке «Редактировать сектор» оставить только базовые данные сектора (Ник, реальное имя, ранг, VIP, Сила, Киллы, Очки, Владелец).
   - Вынести управление офицерами прямо в блок «Офицеры сектора» на странице: кнопка `+ Добавить офицера`, точечное редактирование конкретного офицера (`✏️`), удаление (`🗑️`) и интерактивные звезды/навыки.
5. Обеспечить безопасность при регистрации: новый пользователь может сразу создать свой сектор или нажать «Сделать позже», но не может произвольно забрать чужой сектор из ростера. Привязку свободных секторов из ростера выполняют офицеры (Р4/Р5).

### Не-цели (Non-Goals)
- Физическое переименование таблиц базы данных SQLite (`players` ➔ `sectors` не требуется; сохраняется обратная совместимость схемы и всех экспортов/импортов).
- Изменение механики автопика мест в ивентах (в событиях участвуют базы/секторы, как и ранее).

### Анти-цели (Anti-Goals)
- Нельзя требовать обязательного наличия пользователя для каждого сектора (офицеры Р4/Р5 должны иметь возможность вести общий ростер соклановцев, даже если те еще не зарегистрировались на сайте).
- Нельзя допускать самовольный захват секторов соклановцев новыми пользователями при регистрации.

## 2. Анализ подходов (Approaches)

### Подход 1: Сквозная модель 1:N с сохранением обратной совместимости схемы (Выбран)
- В таблице `players` добавляется колонка `user_id INTEGER REFERENCES users(id)` через автомиграцию.
- Связи из `users.player_id` переносятся в `players.user_id`.
- На уровне API и клиентского интерфейса вся терминология переходит на «Сектор».
- Добавляются точечные эндпоинты управления офицерами сектора (`/api/players/:id/officers`).
- **Плюсы:** 100% обратная совместимость со старыми бэкапами и JSON экспортами v2/v3, нулевой риск потери данных, плавный переход.

### Подход 2: Жесткое переименование таблиц в SQLite (`sectors`, `sector_officers`)
- Пересоздание таблиц БД и полный разрыв со старой схемой.
- **Минусы:** Ломает существующие файлы баз данных без сложных многоступенчатых миграций, требует переписывания всех SQL-запросов и импортов.

## 3. Детальный дизайн решения

### 3.1. Схема базы данных и миграции ([db.js](file:///Users/ranunkulus/Downloads/KOW/db.js))
1. **Колонка `user_id` в таблице `players` и сохранение `users.player_id`:**
   - Добавляется колонка `user_id INTEGER NULL REFERENCES users(id) ON DELETE SET NULL`.
   - Колонка `users.player_id` сохраняется как указатель на текущий **активный сектор** пользователя (обеспечивает 100% обратную совместимость для сессий, авторизации `req.user.playerId`, отладки).
   - В `initDb()` выполняется безопасная миграция: если у пользователя в таблице `users` заполнен `player_id`, проставляется `UPDATE players SET user_id = users.id WHERE id = users.player_id AND user_id IS NULL`.
2. **Выборка секторов:**
   - В `getPlayers()` и `getPlayerById(id)` выполняется `LEFT JOIN users u ON u.id = p.user_id`, возвращая поля:
     - `userId`: `p.user_id`
     - `username`: `u.username`
     - `userRank`: `u.rank`
3. **Метод `getPlayersByUserId(userId)`:**
   - Возвращает все секторы, принадлежащие данному пользователю.
4. **Обновление привязки владельца:**
   - В `updatePlayer(id, updates)` разрешается обновление `user_id` (только для Р5/Р4).

### 3.2. REST API ([server.js](file:///Users/ranunkulus/Downloads/KOW/server.js))
1. **`/api/my-profile` и переключение активного сектора:**
   - Для авторизованного пользователя возвращает:
     - `user`: `{ id, username, rank }`
     - `sectors`: массив всех секторов пользователя `[{ id, name, sector, stock, officers, ... }]`
     - `activeSectorId`: ID текущего выбранного сектора (по умолчанию `user.player_id` или первый сектор пользователя).
     - Сохраняет обратную совместимость: поля `sector`, `stock`, `officers` на верхнем уровне соответствуют активному сектору.
   - `POST /api/my-profile/active-sector`: принимает `{ sectorId }`. Обновляет `users.player_id = sectorId` (только если сектор принадлежит пользователю), обеспечивая персистентность активного сектора между сессиями.
2. **`POST /api/my-sectors`:**
   - Позволяет пользователю создать новый сектор для себя (указывается `name`, опционально `realName`). Созданный сектор автоматически получает `user_id = req.user.id`. Если у пользователя еще не было активного сектора, новый сектор становится активным (`users.player_id = newSectorId`).
3. **Унифицированный `PUT /api/players/:id`:**
   - Доступен руководству альянса (`r4`, `r5`) и владельцу сектора (`r3`), если `player.user_id === req.user.id`.
   - При запросе от Р3 системные поля (`rank`, `id`, `user_id`) строго игнорируются/санитизируются.
   - Используется как модальным окном сектора (`#modal-sector`), так и личным кабинетом (`my_cabinet`).
4. **Точечный CRUD офицеров сектора:**
   - `POST /api/players/:id/officers` — добавление офицера в сектор. Доступно владельцу сектора (Р3) и офицерам альянса (Р4/Р5).
   - `PUT /api/players/:id/officers/:offId` — обновление уровня, купонов, звезд, навыков конкретного офицера.
   - `DELETE /api/players/:id/officers/:offId` — удаление офицера из сектора.
5. **Мульти-регистрация на ивенты (`/api/events`):**
   - `POST /api/events/:id/register`: принимает `{ officerId, desiredPlace, sectorId }`. Если `sectorId` опущен, используется активный сектор. Проверка прав: пользователь должен владеть данным сектором (`sector.user_id === req.user.id`) либо иметь ранг Р4/Р5.
   - `DELETE /api/events/:id/register`: принимает `?sectorId=...` или тело с `sectorId`.
   - `GET /api/events`: возвращает массив всех заявок пользователя по его секторам (`myRegistrations: [...]`) и `myRegistration` для активного сектора для обратной совместимости.
6. **Доступ к списку пользователей для привязки (`GET /api/users`):**
   - Права на `GET /api/users` расширяются для `['r4', 'r5']` (список возвращает только безопасные публичные поля: `id`, `username`, `rank`, `playerName`).
   - Мутации пользователей (`PATCH /api/users/:id` — смена паролей, роли Р5) остаются строго за Р5.

### 3.3. Пользовательский интерфейс (UI)

#### А. Терминология и навигация ([index.html](file:///Users/ranunkulus/Downloads/KOW/index.html), [app.js](file:///Users/ranunkulus/Downloads/KOW/app.js))
- Пункт меню: **«👥 Игроки» ➔ «🏰 Секторы»** (`nav-sectors`).
- Заголовки страниц: «Секторы альянса», «Карточка сектора».
- В таблице секторов:
  - Колонки: «Сектор (База)», «Владелец», «Ранг», «VIP / Конф.», «Сила / Киллы», «Очки за убийство», «Действия».
  - В колонке «Владелец»: кликабельный бейдж `👤 @username` (если привязан) или приглушенный бейдж `Без владельца`.

#### Б. Личный кабинет (`Мой кабинет`)
- В шапке кабинета отображается переключатель секторов пользователя:
  ```html
  <div class="cabinet-sectors-bar">
    <span class="label">🏰 Активный сектор:</span>
    <select id="cabinet-sector-select" onchange="switchCabinetSector(this.value)">
      <option value="1">[A433]ranu (Мейн · 157.6M)</option>
      <option value="2">[A433]ranu_farm (Ферма · 32.1M)</option>
    </select>
    <button class="btn btn-secondary btn-sm" onclick="openAddSectorModal()">+ Добавить сектор</button>
  </div>
  ```
- Если у пользователя ещё нет секторов (нажал «Сделать позже» при регистрации):
  - Показывается информационный блок с приветствием и кнопкой `🏰 Создать свой первый сектор (базу)`.

#### В. Регистрация нового пользователя
- В модальном окне регистрации (`#modal-auth`):
  - Поле `Название вашего сектора (базы в игре)` с подсказкой: *«Опционально. Вы можете указать игровой ник сейчас или добавить базу позже в личном кабинете»*.
  - Выбор из существующего ростера исключен для предотвращения ошибок и захвата чужих баз.

#### Г. Декомпозиция карточки Сектора (`renderPlayerDetail`)
1. **Шапка карточки:**
   - Название сектора, реальное имя, статы (VIP, Конф, Сила, Киллы, Очки за убийства).
   - Бейдж владельца: `👤 Владелец: @username`. Для Р4/Р5 рядом кнопка `Изменить владельца` (выпадающий список пользователей).
   - Кнопка `Редактировать сектор`: открывает модальное окно `#modal-sector`, содержащее **только** общую информацию сектора (Ник, реальное имя, ранг, VIP, Сила, Киллы, Очки, Владелец) и кнопку Smart Scanner.
2. **Блок «Офицеры сектора»:**
   - В заголовке блока: кнопка `+ Добавить офицера` (открывает компактную модалку `#modal-add-sector-officer`).
   - В строке каждого офицера в таблице:
     - Интерактивные звёзды.
     - Кнопка `✏️` — открывает компактное окно редактирования именно этого офицера (уровень, купоны, звёзды, навыки 1–4).
     - Кнопка `🗑️` — быстрое удаление офицера с подтверждением.

#### Д. Регистрация на ивенты (`#modal-event-register`, календарь)
- Если у пользователя более одного сектора, в форме регистрации отображается выбор сектора (`Сектор для участия`).
- Список офицеров динамически подгружается для выбранного сектора.
- В календаре и на странице ивента отображаются плашки поданных заявок по каждому сектору пользователя с возможностью их отдельного редактирования или отмены.
