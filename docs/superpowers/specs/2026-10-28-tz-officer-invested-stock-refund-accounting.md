## 1. Введение и анализ требований пользователя

По результатам тестирования релиза v3.16.1 и анализа пользовательского опыта сформированы две ключевые задачи:

### 1.1. Проблема 1: Искажение баланса при возврате ресурсов на склад
- **Симптом:** Если на офицера потратили, например, 253 000 купонов звезды и 190 000 очков в готовых звёздах со склада, то при понижении уровня звёзд или отмене на склад возвращаются **исключительно купоны звезды**, а списанные готовые звёзды III, II, I сгорают.
- **Причина:** Функции расчета дельты склада в `logic.js` были реализованы без сохранения состояния (*stateless*), и при понижении (`delta < 0`) весь возврат принудительно пересчитывался в купоны.
- **Согласованное решение (Вариант 1):** Хранить в карточке каждого офицера структуру `officer.invested` с точным количеством списанных со склада ресурсов. При понижении звёзд или навыков возвращать ровно то, что было списано, по принципу **LIFO** (сначала ценные звёзды/медали, затем купоны).
- **Правило для офицеров вне трекера:** Если офицер был прокачан до появления трекера или добавлен вручную (у него `invested` равен 0), при его понижении склад **НЕ пополняется фиктивными ресурсами** (`delta = 0`). Офицер просто понижается.

### 1.2. Проблема 2: «Портянка» офицеров в таблице секторов и отсутствие сортировки по поколениям
- **Симптом (скриншот пользователя):** В таблице «Секторы альянса» в колонке «ОФИЦЕРЫ» список офицеров выводится сплошным неструктурированным списком без сортировки по поколениям. При наличии 5–15 офицеров ячейка превращается в огромную «портянку», растягивающую строку таблицы на пол-экрана.
- **Согласованное решение:**
  1. **Компактный вид в таблице секторов:** Отображать строго **топ-2 самых старших по поколению офицеров** сектора. Если у сектора есть ещё офицеры, под ними выводить аккуратный бейдж-ссылку: **`+ ещё N офицеров`** с всплывающей подсказкой (тултипом) полного списка при наведении и переходом на страницу сектора по клику.
  2. **Сквозная сортировка по поколению (убывание):** Офицеры должны сортироваться от старших поколений к младшим (**Gen 9 ➔ Gen 8 ➔ Gen 7 ➔ ...**, при равенстве поколений — по уровню / звёздам / алфавиту) во всех разделах системы:
     - В ячейке «Офицеры» общей таблицы «Секторы альянса»;
     - В таблице «Офицеры сектора» на детальной странице сектора (`renderPlayerDetail`);
     - В карточках офицеров в Личном кабинете (`renderMyCabinet`);
     - В общем Каталоге офицеров (`renderOfficers`).

### 1.3. Проблема 3: Срез чисел функцией parseInt при наличии пробелов (аномалия «До VIP 14 осталось 749 938 очков»)
- **Симптом:** При уровне VIP 13 и накопленных 629 500 очках VIP подсказка прогресса выводит: *«⭐ До VIP 14 осталось 749 938 очков (+1 пазлов/день)»*.
- **Причина:** В функции `updateVipProgressHint` (и аналогичных функциях живого обновления) значение поля считывалось через нативный `parseInt(ptsInput?.value)`. При наличии пробелов в строке вида `"629 500"` стандартный `parseInt` останавливается на пробеле и считывает только начало строки, возвращая `629` (или `62` при частичном вводе), из-за чего из 750 000 вычитается не полное число, а его обрубок.
- **Согласованное решение:** Во всех обработчиках живых расчетов и подсказок (включая `updateVipProgressHint`, `updateCabinetLiveStars`, `updateSectorLiveStars`, `saveSectorInline`) заменить `parseInt` на надежную утилиту `parseInputNumber`, которая удаляет все пробелы перед парсингом. При 629 500 накопленных очках до VIP 14 (порог 750 000) трекер будет точно отображать:
  $$750\,000 - 629\,500 = \mathbf{120\,500} \text{ очков осталось}.$$

## 2. Архитектура: Модель инвестиций офицера (`officer.invested`)

### 2.1. Структура `invested` в объекте офицера
В карточке каждого офицера сектора (`player_officers`) фиксируются фактически списанные со склада трекера ресурсы:
```javascript
officer.invested = {
  starCoupons: 0,       // списано купонов звезды
  legendaryStars1: 0,   // списано звёзд I (110 очков)
  legendaryStars2: 0,   // списано звёзд II (420 очков)
  legendaryStars3: 0,   // списано звёзд III (960 очков)
  coupons: 0,           // списано купонов офицера
  puzzles: 0            // списано универсальных медалей офицера
};
```

### 2.2. Защита от дюпа для офицеров вне трекера
- Для всех офицеров, уже существовавших в базе до внедрения системы инвестиций, или созданных вручную с ненулевым уровнем/звёздами, объект `invested` инициализируется нулями.
- При понижении звёзд, навыков или уровня у такого офицера на склад начисляется ровно **0 ресурсов** (`delta = 0`). Склад сектора защищен от генерации ресурсов «из воздуха».

## 3. Детальные алгоритмы списания и возврата склада

### 3.1. Списание ресурсов (Повышение параметров)
1. **Проверка достаточности ресурсов на складе:**
   - Строгий приоритет:
     - **Звёзды:** Сначала купоны звезды `stock.starCoupons`, затем готовые звёзды со склада `stock.legendaryStars3` (960), `stock.legendaryStars2` (420), `stock.legendaryStars1` (110).
     - **Навыки и уровни:** Сначала купоны офицера `stock.coupons`, затем медали `stock.puzzles`.
   - Если ресурсов на складе не хватает — операция отклоняется (`canAfford: false`), параметры офицера не изменяются, выводится тост с точным дефицитом.
2. **Фиксация инвестиций:**
   - Со склада сектора списываются: `stock.item -= deductedItem`.
   - В `officer.invested` эти же количества **прибавляются**:
     ```javascript
     officer.invested.starCoupons += deductedStarCoupons;
     officer.invested.legendaryStars3 += deductedStars3;
     officer.invested.legendaryStars2 += deductedStars2;
     officer.invested.legendaryStars1 += deductedStars1;
     officer.invested.coupons += deductedCoupons;
     officer.invested.puzzles += deductedPuzzles;
     ```

### 3.2. Возврат ресурсов (Понижение параметров)
1. Вычисляется сумма очков понижения: `pointsToRefund`.
2. Если `officer.invested` пуст (все нули) — на склад ничего не возвращается (`delta = 0`).
3. Если в `officer.invested` есть вложения:
   - Ресурсы возвращаются **строго из пула `officer.invested`** по принципу **LIFO**:
     - **Звёзды:**
       1. Сначала восстанавливаются звёзды III (в пределах `officer.invested.legendaryStars3`, по 960 очков).
       2. Затем звёзды II (в пределах `officer.invested.legendaryStars2`, по 420 очков).
       3. Затем звёзды I (в пределах `officer.invested.legendaryStars1`, по 110 очков).
       4. Оставшаяся часть очков начисляется в `starCoupons`, но **не более**, чем числится в `officer.invested.starCoupons`.
     - **Навыки и уровни:**
       1. Сначала восстанавливаются универсальные медали `puzzles` (в пределах `officer.invested.puzzles`).
       2. Затем восстанавливаются купоны `coupons` (в пределах `officer.invested.coupons`).
   - Склад сектора пополняется на фактически возвращенные ресурсы (`stock.item += refundedItem`).
   - Из `officer.invested` вычитаются возвращенные ресурсы (`officer.invested.item -= refundedItem`).
   - **Итог:** На склад возвращаются ровно те же самые предметы, которые были потрачены.

### 3.3. Моментальный откат через тост `[↩ Отменить]`
- Перед операцией формируется полный снимок состояния:
  ```javascript
  const snapshot = {
    stock: structuredClone(currentStock),
    officer: structuredClone(currentOfficer)
  };
  ```
- При клике по кнопке `[↩ Отменить]` состояние склада и офицера мгновенно восстанавливается из `snapshot` байт в байт.

## 4. Компактное отображение офицеров и сквозная сортировка по поколениям

### 4.1. Сортировка офицеров по убыванию поколения (Gen Sort Helper)
В `logic.js` добавляется чистая функция сортировки:
```javascript
function sortOfficersByGeneration(officers, catalog) {
  // Сортировка по убыванию:
  // 1. Поколение каталога (generation: 9 -> 8 -> 7 -> ...)
  // 2. Уровень звёзд (stars: 6 -> 5 -> ...)
  // 3. Уровень офицера (level: 180 -> ...)
  // 4. Имя офицера (алфавит)
}
```

### 4.2. Таблица «Секторы альянса» (Колонка «ОФИЦЕРЫ»)
- Офицеры сектора сортируются с помощью `sortOfficersByGeneration`.
- В ячейке выводятся **строго топ-2 самых старших по поколению офицера**:
  ```html
  <div class="sector-officers-compact-list">
    <!-- Топ-1 старший офицер -->
    <div class="officer-compact-row">...</div>
    <!-- Топ-2 старший офицер -->
    <div class="officer-compact-row">...</div>
    
    <!-- Бейдж для остальных офицеров -->
    <div class="officers-more-badge" 
         onclick="navigate('player_detail', {id: ${p.id}})"
         data-tooltip="Остальные офицеры: ${otherOfficersList}"
         title="Остальные офицеры: ${otherOfficersList}">
      + ещё ${remainingCount} офицеров
    </div>
  </div>
  ```
- Высота ячейки фиксируется, устраняется вертикальное раздувание строк таблицы.
- При наведении на бейдж `+ ещё N офицеров` отображается стилизованный тултип с именами, поколениями и уровнями остальных офицеров. При клике — мгновенный переход на детальную страницу сектора.

### 4.3. Таблица «Офицеры сектора» на странице «Сектор» (`renderPlayerDetail`)
- Список офицеров сектора сортируется по убыванию поколения: старшие поколения (Ген. 9, Ген. 8) отображаются вверху таблицы, младшие — внизу.

### 4.4. Личный кабинет (`renderMyCabinet`)
- Сетка карточек офицеров сектора сортируется по убыванию поколения (старшие поколения отображаются первыми).

### 4.5. Каталог офицеров (`renderOfficers`)
- Список каталога командиров сортируется по убыванию поколений: S9 ➔ S8 ➔ S7 ➔ ...

## 5. Изменения в БД SQLite и REST API

### 5.1. Схема базы данных SQLite (`db.js`)
В функции `initDb()`:
```sql
ALTER TABLE player_officers ADD COLUMN invested_json TEXT NOT NULL DEFAULT '{}';
```
- Добавление и обновление офицера сохраняет `invested_json`.
- Чтение офицера восстанавливает `invested: JSON.parse(row.invested_json || '{}')`.
- Обратная совместимость в `exportKowJson` / `importKowJson` (старые дампы получают пустой `invested`).

### 5.2. REST API (`server.js`)
- Эндпоинты `PUT /api/my-profile/officers/:id` и `PUT /api/players/:id/officers/:id` валидируют и сохраняют поле `invested`.
